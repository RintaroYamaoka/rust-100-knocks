# 2026-08-30 — 言語セレクタが遅い回線で最大 16 秒 Rust しか出ない

## 何が起きたか

7 言語 2100 問を本番デプロイした直後、利用者から「Rust しか選べない」と報告。
再現したところ、言語一覧が揃うまで **最大 16 秒** かかっていた。

| 回線 | 7 言語が揃うまで |
|---|---|
| 高速 | 445ms |
| 3G 相当 (400kbps/400ms RTT) | 13,482ms |
| 低速 3G (200kbps/600ms RTT) | 16,308ms |

原因は、言語一覧を **21 本の HEAD リクエストを逐次** 投げて決めていたこと
(`Language::ALL` × `Level::ALL` を二重ループで `.await`)。揃うまでセレクタには
Rust しか出ない。

## なぜ検証をすり抜けたか

これが本題。**検証は「7 言語すべて出る」ことを確認していて、実際に出ていた。**
見落としたのは *いつ* 出るかだった。

1. **高速回線でしか測っていなかった** — 開発機から Vercel の edge までは速く、
   445ms なので体感で気づかない。ネットワークを絞った検証をしていなかった
2. **ハーネスが待ってしまっていた** — `verify.mjs` に
   `await page.waitForTimeout(2500)` と書いてあった。「存在確認が終わるのを待つ」
   つもりのコードが、**遅さそのものを隠していた**。待ち時間を入れた時点で、
   その待ち時間より遅い問題は永久に見えない
3. **DoD が「出る」としか言っていなかった** — WO の D9 は
   「言語を切り替えられ、切り替えると一覧が追従する」。*何秒で* を書いていない
   ので、16 秒かかっても DoD は満たされる

3 回のレビュー (事前 / 統合前 / 再判定) も、いずれも静的な読みとローカル実行で、
回線条件は観点に入っていなかった。

## 対処

### 直したもの

ビルド時に収録済み言語のマニフェスト (`data/problems/index.json`) を実ファイルから
生成し、フロントは 1 本読むだけにした (`scripts/gen-manifest.mjs`)。

  高速 16ms / 3G 11ms / 低速3G 12ms  (リクエスト 21 本 → 2 本)

待ち時間が回線速度に依存しなくなり、「1 本でも瞬断すればその言語が消える」脆さも
同時に消えた。マニフェストが取れない場合の退避 (404 / 壊れた JSON / 空) も実測済み。

### 教訓

- **待ち時間を入れたテストは、その待ち時間より遅い問題を隠す。**
  `waitForTimeout(N)` で待つのではなく、「揃うまでの時間」を測って上限で判定する
- **「動く」を確認したら「どれだけ速く動くか」も測る。** 起動時にネットワークを
  叩く設計は、開発機の速さで隠れる。ネットワークを絞った検証を必ず 1 本入れる
- **起動時に N 本のリクエストを逐次投げる設計は避ける。** 1 本にできるなら 1 本にする。
  逐次だと N × RTT が丸ごと待ち時間になり、どれか 1 本の失敗が機能欠落になる
- DoD に体験の条件 (何秒以内か) を書けるものは書く

## 再発防止

- `scripts/gen-manifest.mjs` + そのテスト (`npm run test:manifest`)
- ブラウザ検証ハーネスに回線エミュレーション付きの計測を追加
  (`scratchpad/pw/speed.mjs` — 3 段階の回線でセレクタが埋まるまでを測る)
- CLAUDE.md の「既知の地雷」に、起動時の逐次リクエストについて追記
